# Session Board

**Purpose:** coordination for multiple concurrent Claude sessions on this project. **Mathew does not manage this board — the sessions do.**

**This file is the single canonical rulebook for multi-session work — `CLAUDE.md` only points here. You (the session) own this file. On your first file read/edit, read this board — it is the live availability map. Add your own claim row BEFORE touching any file, keep its status current, and move it out when the work is done. Never ask Mathew to touch the board.**

**What collides in THIS repo** (it is not the same as a hand-apply project): the same `.cs` file edited by two sessions is a real git conflict; the **shared build output** (`Plugin\bin`, `Plugin\obj`) means two builds running at once produce a mangled DLL and a nonsense error; the **single dev profile** every debug build copies into means the last build wins regardless of who ran it; and the **single Unity project** cannot be open twice.

---

## Protocol (the rules)

1. **Read before you touch.** On your first file operation of the session, read this board. **Only an *Active claims* row with status `authoring` or `building` is a LOCK** — those files belong to another session. A row marked `done`, and anything in **History**, is RELEASED. Everything not in an active `authoring`/`building` row is free.
2. **Claim atomically.** Before editing anything, add a row to *Active claims* and take your batch number by editing the counter below with an EXACT content match: `next = N` → `next = N+1`. If that exact-match edit fails, another session bumped it first — re-read the board and retry with the new number. After your claim lands, re-read the board once to confirm your row survived intact; a clobbered write must not go unnoticed.
3. **Claims are terse and canonical.** The *Files* column IS the lock: a bare list of canonical paths (`Plugin\src\Enemy\LethalGargoylesAI.cs`, `Plugin\src\Utility\AudioManager.cs`, `ToDo.md`) — never prose. A sibling must be able to find a lock by scanning for the real file name at a glance. Scope, caveats and design notes go in *Notes*.
4. **The board is the lock.** If a file you want is in an active claim, work around it. If your task can't proceed without it, tell Mathew it's blocked and on which session — don't silently edit it. Two active claims may share a file ONLY when both rows name each other explicitly and one session is the designated merge owner — keep that rare and deliberate.
5. **CLAIM THE BUILD.** `dotnet build` is not a read-only act here: it writes `Plugin\bin`, `Plugin\obj`, runs the netcode patcher over the output, and **copies into the shared Gale `Dev` profile**. Take the lock `BUILD` in your *Files* column and set your status to `building` for as long as it runs. Two concurrent builds produce a corrupt DLL and an error message that describes neither cause. If you see an active `building` row, wait — a build is seconds, not minutes.
6. **Re-check blocked files before you say "waiting."** Locks clear while you work. Right before posting any final message that reports you're blocked on (or deferred work around) a claimed file — and at natural checkpoints in a long session — re-read this board. If the blocking claim is gone or `done`, DO the deferred work now instead of reporting you're still waiting. Reporting "blocked" without a fresh board read is a protocol violation.
7. **Stale claims can be challenged.** Bump your row's *Updated* date every time its contents or status move. Sessions die (closed window, exhausted context): an `authoring` row whose *Updated* is a prior day is suspect — ask Mathew whether that session is still open. Once he confirms it's dead, move the row to History marked `abandoned`; its files are free.
8. **Pick your lane.** Prefer work inside one domain lane (below) to minimise collisions. Audio, AI and Unity-side work rarely overlap.
9. **Single-writer shared docs.** `ToDo.md`, `CHANGELOG.md`, `CLAUDE.md` and this board collide easily. Claim them like any other file, and always edit with content-anchored matches, never line numbers — they go stale the instant another session writes.
10. **Park work Mathew owes, where it can't be lost.** Code compiling is NOT the same as working. If your batch needs something only he can do — **rebuild `gargoyleassets` in the Unity Editor**, record or export a voice line, run the game and confirm behaviour, bump a version number — put it in ***Pending manual steps*** below BEFORE your row leaves *Active claims*. A note that only rides a History row gets trimmed and lost. Delete the step the moment it's confirmed done.
11. **Move your row out when you're finished.** Flip to `done`, park anything owed under *Pending manual steps*, then move the row to *Recently done* — and when that table passes ten rows, move the oldest into `Docs\Archive\Session_Board_History.md` **verbatim**. Trimming is a MOVE, never a delete: these rows carry findings that exist nowhere else.
12. **Git is real here.** Commit only when Mathew asks. If you do, one batch = one commit, and say the batch number in the message. Never commit `Plugin\bin`, `Plugin\obj`, `UnityProject\Library`, `.vs`, or `.claude\worktrees`. **Ignore coverage — corrected 2026-08-15 (b2): there are FOUR `.gitignore` files and all of them are tracked** — a root one (added by b2), plus `Plugin\`, `UnityProject\` and `AssetSources\`. b1's note here claimed there were two and that neither was tracked; both halves were wrong, off a `git ls-files | grep` whose exit status silently ate the result. **`git ls-files --error-unmatch <path>` is the check that cannot lie about whether a file is tracked** — use it instead of grepping a listing. Staging explicit paths is still the better habit, but `git add -A` from the root is no longer the hazard it was.
