## 2026-08-16 — Gargoyle Statue duplication: an audit finding I shipped was wrong (board b13)

**The bug:** activating a Gargoyle Statue played one taunt per connected machine. Two players, two overlapping voices. Mathew first saw it as "hold 2 statues, get 2 taunts".

**The cause was a b8 change made on a FALSE audit finding.** `Optimization_Audit.md` C1 said `GargoyleStatue.ItemActivate` wrongly gated its `ItemActivateServerRpc` send behind `IsServer`, reasoning that a `RequireOwnership = false` ServerRpc exists so non-authoritative clients can send it — so gating on `IsServer` must mean only the host can ever trigger the statue. **Two independent audit agents reached that conclusion and both were wrong.**

**`GrabbableObject.ItemActivate` is REPLICATED BY VANILLA to every machine.** It does not run only on the activating client. The instrumented log is unambiguous: the host runs it for a client-held item — `server=True owner=False heldBy=Player #1`. So the `IsServer` guard was load-bearing: it made exactly one machine forward the request. **The statue was never mute for non-hosts** — the host's replicated copy had always fired the taunt, which is why no player had ever reported silence. Removing the guard turned a non-bug into a real one. Reverted in `48d5e64`; the trap is now in `CLAUDE.md` → *Do-not-relearn*, along with the corrected general rule: **"guard RPC sends with `IsServer`" is not only about ClientRpcs — a ServerRpc sent from a vanilla-replicated callback needs it too, for a different reason.**

**THE PROCESS FAILURE IS THE MORE USEFUL RECORD.** The first repro was "2 statues held → 2 taunts" **with 2 players connected**. Item count and machine count were both 2. This session anchored on item count and shipped **two** wrong fixes at that target — a `GrabbableObject.isPocketed` guard, twice — before instrumenting anything. What broke the deadlock was Mathew changing the experiment, not another hypothesis: **one single-player run with 2 statues produced 1 taunt**, which eliminated item count outright. Recorded in `CLAUDE.md`: *when a repro has two candidate multipliers sitting at the same number, vary one before theorising.*

**What survived from the wrong turns:** `isPocketed` is kept on the `Update()` dog-taunt path, where it is genuinely correct — `GrabbableObject.Update()` really does tick for every item in an inventory, so four carried statues really would all bark at an Eyeless Dog. That half was a real bug; it was just not this one.

**Also shipped, at Mathew's request:** a server-side talk reservation keyed by client id — **one talking statue per player**, so carrying four gives one voice. Plus a per-statue floor against spam-clicking. This replaces the old `!scrapAudio.isPlaying` check, which could never have worked: clips play through `PlayOneShot`, and one-shots do not reliably drive `isPlaying`.

**Method note worth keeping:** the whole thing was settled by logging `NetworkObjectId` at all three candidate sites (send / ServerRpc receive / ClientRpc play) and reading one press. The `[H]`/`[C]` host-client tag from the b7 diagnostic layer is what proved the duplication was cross-machine rather than cross-item.

## 2026-08-15 — procedure skills + standing subagent authorization (board b4)

Four **procedure skills** authored, and subagent use wired in as standing policy. Docs and `.claude\` only — no `Plugin\src`, no build.

**The distinction that makes the skills worth having:** the two existing skills (`deep-work`, `light-touch`) carry no procedure at all — their whole job is to move the model/effort dial. The four new ones carry **steps**: `voice-line`, `game-update`, `ship-release`, `playtest`. Each exists because the procedure spans several files, **fails quietly when a spot is missed**, and is otherwise reconstructed from scratch every time. Skills that merely restate `CLAUDE.md` were deliberately not written — a skill has to earn its place by encoding something a session would otherwise get wrong.

**THE SKILL WORK IMMEDIATELY PAID FOR ITSELF, AND NOT IN THE WAY EXPECTED.** Before writing the `voice-line` skill, an `Explore` agent was sent to verify the "adding a category is a six-place change" claim this file and `CLAUDE.md` had both been publishing. **It is seven, and the missing one matters: `Scrap\GargoyleStatue.cs` carries its OWN parallel copy of the `clipType` switch.** Miss it and the monster taunts correctly while the scrap silently plays nothing — a difference nobody would think to test for, produced by a doc that was confidently wrong. A third, optional switch in `LethalGargoylesAI.OtherTaunt` (only 4 categories) turned up too. **b1 wrote that six-place claim from reading the code directly; a cheap sweep by a `haiku` agent found what a careful read had missed.** Corrected in `CLAUDE.md`, and the verified table now lives in the skill.

**`game-update` ships a runnable tool, not just prose.** `.claude\skills\game-update\reflect.cs` is a .NET 10 single-file app — `dotnet run reflect.cs EntranceTeleport` prints the real fields, properties and methods of any vanilla type off the installed assembly, with a `~Prefix` mode for finding a type whose name you half-remember. It loads nothing, needs no running game, and **shows private members**, so the publicizer can never confuse "missing" with "inaccessible". Verified working in both modes; `#:property EnableTrimAnalyzer=false` suppresses the trim warnings that otherwise bury the output. **This is the tool that settled `exitPoint` in b3 in minutes, promoted from a one-off in a scratch folder to something the next session finds by name.**

**Subagents are now standing policy** (`CLAUDE.md` → *Subagents*). Mathew asked for it permanently, which resolves the VS Code extension's injected *"Do not call the AgentTool unless the user requested it"* — that line comes from a file nobody can edit, so it is recorded here as satisfied rather than re-asked every session. The delegation table is concrete about *why* it matters here: `LethalGargoylesAI.cs` is ~2,900 lines, and answering "where does X happen" by reading it at the session model is the most wasteful thing a session can do.

**Three rules keep delegation from breaking the board, and they are the non-obvious half:** a subagent never claims/edits/releases a board row (the parent owns it end to end — a subagent bumping the batch counter races every other session), a subagent never runs `dotnet build` (the output folder, netcode-patch pass and Gale profile are shared), and subagents default to read-only. **A parallel fan-out of writers would defeat the entire locking scheme the board exists to provide.**


Took b2's parked csproj item once the game was reinstalled, and found a bigger thing on the way in.

**THE GAME UPDATED UNDER v0.7.0 AND ITS SOURCE NO LONGER COMPILED — this was sitting in the repo before any of this work started.** The baseline build (run *before* touching the csproj, precisely so a failure could be attributed) came back with one error: `EntranceTeleport` has no `exitPoint`. **It was deleted from the game, not renamed.**

**How that was settled without guessing, which is the part worth keeping.** Grepping `Assembly-CSharp.dll` for `exitPoint` finds hits and is *misleading* — the string survives in the metadata heap because `exitPointDoesntExist` shares the prefix. What actually answered it was reflecting over the installed assembly with a `MetadataLoadContext` (a .NET 10 single-file script, `#:package System.Reflection.MetadataLoadContext`, a `PathAssemblyResolver` over the game's `Managed\` folder): it loads nothing, needs no game running, and lists **private members too**, so publicizer behaviour cannot muddy the answer. The current shape is `public EntranceTeleport exitScript` + `public Transform entrancePoint`, with `bool FindExitPoint()` resolving the pairing and reporting whether one exists. PathfindingLib corroborates it — that DLL references `entrancePoint` and `isEntranceToBuilding` and never `exitPoint`. **The recipe is now in `CLAUDE.md` → Do-not-relearn, because the game will do this again.**

The fix routes the one call site through `FindExitPoint()` then `exitScript.entrancePoint`, which also supplies **the null guard the old `exitPoint` read never had**. **Exactly one call site broke** — C# reports all CS1061s in a pass, so the single error is itself evidence the rest of the API surface still matches. **It is compile-verified and NOT game-verified**, and is parked in `ToDo.md` under an in-game check with a description of what "wrong" would look like (coming out the same side it went in).

**The csproj work itself, now verifiable:**
* `CopyNVorbis` resolves through `$(NuGetPackageRoot)` instead of a literal `C:\Users\mathe\.nuget\...`, with the version in a single `$(NVorbisVersion)` property the `PackageReference` shares — so the restored package and the copied DLL **cannot** drift. It also gained an `<Error>` guard, because the old form would have quietly copied nothing if the path ever went stale.
* `Unity.Collections` / `Unity.Mathematics` moved off depth-sensitive `..\..\..\..\Program Files\...` walks into the existing `$(CI) != 'true'` group on `$(ManagedDirectory)`. **Bonus defect closed by the same edit: they had no `Private="false"`, so every build was copying two game assemblies into `bin\`.** Confirmed gone afterwards.
* **Verified in three steps, not by declaration:** `dotnet msbuild -t:CopyNVorbis` standalone (both files copied, 0 errors); a rebuild showing the *same single* pre-existing error and no new ones — which proves the moved references resolve, since `AudioManager` uses `Unity.Collections.Allocator` and would have failed loudly; then the green build after the compat fix. **0 errors, 0 warnings**, netcode patcher confirmed by `DropDaDeuce.LethalGargoyles_original.dll`, and the Gale `Dev` profile deployed.

**Measured while in there: the asset bundle is Unity `2022.3.62f3` and the game is `2022.3.62f2`** (bundle header vs `globalgamemanagers`; the exe reports `2022.3.62f2 (7670c08855a9)`). One patch letter apart, shipped that way since v0.7.0, so it is a known fact rather than a fire — but it is the first suspect if assets ever fail to load while the DLL clearly did.

**Confirmed from b2's pending list: `git gc` ran (3,053 loose objects → 1 pack, 699.53 MiB, zero loose) and the stale worktree is gone. b2's index changes are STILL UNCOMMITTED** — `HEAD` is unchanged at `decb0d8` and the staged rename/removal are still sitting there, now joined by b3's source changes.

## 2026-08-15 — doc corrections + git structure (board b2)

Fixed the b1 findings that could be fixed safely, reworked the git hygiene, and found two things that outrank both.

**THE GAME IS NOT INSTALLED, SO THE PROJECT CANNOT BE BUILT.** `D:\Program Files\Steam App\steamapps\common\Lethal Company\` is still there, but `Lethal Company_Data\` holds only `Plugins\` and `UnitySubsystems\` — **no `Managed\` folder**, which is where every game-assembly reference in the csproj points. What remains is the debris Steam leaves behind on uninstall: the mod-created `Lethal Gargoyles\`, `Mirage\` and `BoomboxController\` folders, plus `doorstop_config.ini`. **This is why the two machine-specific csproj paths were NOT fixed in this batch** — the change is small and understood, but it is build-affecting and there is currently no way to compile-verify it, and shipping unverifiable build surgery is how a project acquires a mystery. The path in `LethalGargoyles.csproj.user` is not the bug; the folder it names is correct and its contents are gone.

**The README's custom voice-line path was wrong, and the live install proved it rather than the code alone.** `Plugin.Awake` creates `<game root>\Lethal Gargoyles\Custom Voice Lines`; the README told players `<game root>\Custom Voice Lines`. The uninstalled game directory still carries that exact folder **with real user-added OGGs in it** (`Taunt - Aggro\Voicy_Your son of a bitch.ogg`, `Combat Dialog\Hit\funny-fart-216687.ogg`), which is as direct a confirmation as the repo can offer. Fixed, plus a line telling players the folders appear on first launch. **The general lesson: the artifact a program leaves on disk is stronger evidence than the source that creates it, and it was sitting in a folder nobody thought to look in.**

**`manifest.json` now matches `thunderstore.toml`** (LethalLib 1.1.1, Concentus 2.3.0, PathfindingLib 2.4.1). It had been declaring LethalLib 0.16.1 and omitting **PathfindingLib, which is a hard `[BepInDependency]`**. Only the dev-profile copy was affected — `tcli` publishes from the toml — but two files disagreeing is how someone eventually trusts the wrong one. **Concentus is declared by the toml and referenced NOWHERE in `Plugin\`**; it was mirrored rather than dropped, because removing a dependency from a published package is player-facing. Parked in `ToDo.md`.

**Git structure:**
* **Root `.gitignore` added.** The three subtree files (`Plugin\`, `UnityProject\`, `AssetSources\`) are all tracked and stay authoritative for their own trees — they are upstream templates and are easier to re-sync in place. What none of them could cover is the repo root and any future top-level folder, and the concrete hazard was `.claude\worktrees\`, **a full second checkout of this repo** that `git add -A` from the root would have committed into itself.
* **One rule in it is deliberately narrower than instinct: `*.*~`, not a bare `*~`.** The first draft used `*~`, which also matches Unity's `Documentation~` folder convention and immediately ignored a tracked package folder. Caught by `git ls-files -i -c --exclude-standard` — **run that after touching any ignore rule; it lists tracked files a new rule would have swallowed.**
* **Root `.gitattributes` added with an explicit binary list.** `core.autocrlf=true` plus `* text=auto` means git decides text-vs-binary by sniffing, and a wrong guess injects CRLF and corrupts the file. **`gargoyleassets` is the most exposed asset in the repo because it has no extension**; `.aup3`, `.ogg`, `.blend`, `.xcf` and the `Plugin\dlls\` DLLs are now declared too. `AssetSources\` previously had no attributes coverage at all.
* **A filename-case bug was hiding behind `core.ignorecase=true`:** the index carried `Icon.png` while the disk and `thunderstore.toml` both say `icon.png`. Windows reports a clean tree; a case-sensitive filesystem fails the packaging step. Fixed with `git mv -f`. **Verify case with `git ls-files`, never with `ls`.**
* `AssetSources\Audio\__pycache__\pipeclient.cpython-312.pyc` was tracked; untracked with `git rm --cached`.
* **Measured and NOT acted on: 3,053 loose objects, ~720 MB, ZERO packfiles — this repo has never been packed.** `git gc` is the cheapest possible win and is safe (it compresses reachable history, it does not rewrite it). Both it and `git worktree remove` were blocked by the permission classifier because they delete files under `.git\` — parked for Mathew as *Pending manual steps*. The size itself is real content, not garbage: the biggest tracked files are Audacity sources up to 9.3 MB and `Gargoyle.blend` at 6.4 MB. **LFS would suit `AssetSources\`, but migrating existing history to LFS is a rewrite that breaks every clone — that is a decision, not a chore, and nobody should start one unprompted.**

**Index changes from this batch are STAGED, NOT COMMITTED** (the `git rm --cached` and the `git mv`). They are only real once committed.

## 2026-08-15 — docs + coordination scaffold (board b1)

Ported the instruction/concurrent-work structure from `D:\Projects\ShippingHelper` and adapted it to this repo. New: `CLAUDE.md`, `ToDo.md`, `Docs\INDEX.md`, `Docs\Session_Board.md`, this archive, `Docs\Plans\`, and four `.claude` routing lanes (`deep-work`, `light-touch`, `Explore`, `deep-debug`).

**The adaptation that matters, and the reason a straight copy would have been wrong:** ShippingHelper's whole protocol is shaped by one bottleneck — one Mathew and one `.accdb`, with every change funnelling through a serial manual-apply step. Its board therefore guards *staged-but-unapplied* work, and its `CLAUDE.md` spends a section on handing edits back for hand-application. **Neither applies here.** `Plugin\src\**` is ordinary source in an ordinary git repo; Claude edits and builds it directly. What is genuinely shared and genuinely serial in *this* repo is the **build output** — `Plugin\bin`/`obj`, the netcode-patch pass over the DLL, and the copy into the single Gale `Dev` profile — so the board grew a `BUILD` lock (rule 5) that has no ShippingHelper equivalent, and dropped the staging rules that have no meaning here. **Git conflicts, meanwhile, are real here and were explicitly not a concern there.**

**Three doc/code disagreements were measured while reading the source. Filed in `ToDo.md` → Housekeeping, deliberately not fixed in the same batch:**

* **The custom voice-line folder is `<game root>\Lethal Gargoyles\Custom Voice Lines`.** `Plugin.Awake` builds it as `Path.Combine(Path.GetDirectoryName(Paths.ExecutablePath), "Lethal Gargoyles", "Custom Voice Lines")` and creates eleven subfolders under it. `README.md`'s player instructions give the example path **without** the `Lethal Gargoyles` level. This is player-facing, so it is the one worth fixing first — it makes custom lines silently not load, which is indistinguishable from every other silent-audio failure mode in this mod.
* **`Plugin\Thunderstore\manifest.json` and `thunderstore.toml` disagree on dependencies.** The toml (LethalLib 1.1.1, Concentus 2.3.0, PathfindingLib 2.4.1) is what `tcli` publishes; the manifest (LethalLib 0.16.1, no PathfindingLib) is only copied into the dev profile. PathfindingLib is a **hard** dependency in the `[BepInPlugin]` attributes, so the manifest under-declares it.
* **Two machine-specific paths are baked into `Plugin\LethalGargoyles.csproj`** — the `CopyNVorbis` target's `C:\Users\mathe\.nuget\...` literal, and depth-sensitive relative `HintPath`s for `Unity.Collections`/`Unity.Mathematics` where `$(ManagedDirectory)` already exists and cannot drift. (`LethalGargoyles.csproj.user` being machine-specific is by design — that one is not a bug.)

**Also noted, not acted on: there is no `.gitignore` at the repo root**, only under `Plugin\` and `AssetSources\`. `git add -A` from the root is therefore unsafe; stage explicit paths. Recorded as board rule 12.

> **CORRECTED 2026-08-15 by b2 — the sentence above is wrong in both halves.** There are **three** subtree ignore files, not two (`UnityProject\.gitignore` was missed), and **all three are tracked**. The root gap was real and b2 filled it, but the claim as written overstated it. **The cause is worth more than the correction: it came from `git ls-files | grep -i gitignore` returning nothing inside a long `&&` chain — `grep`'s non-zero exit on no-match had eaten the result, and an empty result read as "not tracked" instead of "the check didn't run".** `git ls-files --error-unmatch <path>` answers the same question per file and cannot fail silently. **A negative result from a pipeline is only evidence if you know the pipeline ran.**
