## Hard Rules (C# / Unity / netcode)

* **Nullable is ENABLED** (`<Nullable>enable</Nullable>`). Unity-serialized fields use the `= null!` idiom; keep it. Do not silence a real null warning with `!` on a value the game can genuinely hand you as null — `playerWhoHit`, `targetPlayer` and `RoundManager.Instance` are all nullable in practice.
* **`AllowUnsafeBlocks` is on and `LangVersion` is `latest`, but the target is `netstandard2.1`.** Collection expressions (`[]`) and the C# 12 primary-constructor style already in `PluginConfig` are fine; anything needing a newer BCL is not.
* **Server authority is the whole design.** The AI decides on the server (`IsServer` / `IsOwner` guards in `DoAIInterval`), then fans out with `[ClientRpc]`. **Never make a gameplay decision client-side** — the client half exists only to play audio and animation. Guard every RPC send with `IsServer && NetworkObject != null && NetworkObject.IsSpawned`; `DoAnimationServerRpc`'s neighbourhood already shows the pattern.
* **Any NEW `[ServerRpc]` / `[ClientRpc]` or new `NetworkBehaviour` requires the netcode patcher to have run.** The `NetcodePatch` MSBuild target runs it post-build (`netcode-patch -uv 2022.3.62 -nv 1.12.0 -tv 1.0.0`). A hand-copied DLL that skipped it throws at runtime with an unhelpful reflection error — **that is what an "RPC method not found" or a silent no-op RPC almost always is.** `Plugin.InitializeNetworkBehaviours()` is the other half: it reflects over the assembly and invokes the patcher's generated `[RuntimeInitializeOnLoadMethod]` initializers, and it **deliberately skips `CoronerClass` when Coroner is not loaded** — a soft-dep type whose initializer runs without its dependency present will throw at load.
* **Soft dependencies must never be touched outside their `Is*Loaded` guard.** `Coroner`, `EmployeeClasses` and `EnhancedMonsters` are `SoftDependency` in the `[BepInPlugin]` attributes and their DLLs are referenced from `Plugin\dlls\`. Referencing one of their types from a method that runs unconditionally causes a `TypeLoadException` at JIT time — not at the line you wrote, which is what makes it hard to read in a log. Keep every such call behind `Plugin.Instance.Is<X>Loaded` and inside a `SoftDepends\` wrapper class.
* **Harmony patches:** all patches live in `Plugin\src\Patch\`. Prefer `[HarmonyPostfix]`. A prefix that returns `false` skips vanilla and is a compatibility hazard with every other mod patching the same method — don't add one without saying so explicitly.
* **Per-frame cost is a real constraint.** `Update` and `DoAIInterval` run per gargoyle, and several can be alive at once. The file already carries the mitigations: `AGGRO_EVAL_INTERVAL` / `HIDE_EVAL_INTERVAL` throttles, static caches for AI nodes, railings and kill triggers, and `LogIfSlow` behind `[Conditional("DEBUG")]`. **Add work to a throttled path, not to raw `Update`, and use the existing caches instead of a fresh `FindObjectsOfType`.**
* **Debug logging is `[Conditional("DEBUG")]`** (`Plugin.LogIfDebugBuild`, and the AI's/AudioManager's local copies). Use those for anything chatty. `Plugin.Logger.LogInfo` fires in Release and shows up in every player's log — reserve it for state that actually matters to a bug report.

## Core Architecture

* **Entry point — `Plugin\src\LethalGargoyles.cs` (`Plugin.Awake`), in order:** bind config → probe the three soft deps by GUID → `InitializeNetworkBehaviours()` → load the `gargoyleassets` bundle from the plugin folder → create the eleven `Custom Voice Lines` subfolders → load `EnemyType`/`TerminalNode`/`TerminalKeyword`, register the enemy through LethalLib at `SpawnWeight` on `LevelTypes.All` → `harmony.PatchAll()` → enumerate default clip files → bind a per-clip enable config → optionally register the Gargoyle Statue scrap → cache `sfx_Step`.
* **AI — `Plugin\src\Enemy\LethalGargoylesAI.cs` (~2,900 lines), `EnemyAI` + PathfindingLib's `ISmartAI`.** It is sectioned with numbered banner comments; **navigate by those, not by line number:** 1) types 2) constants + static caches 3) fields 4) Unity lifecycle 5) state machine 6) movement / smart path / teleport 7) hiding / cover 8) target selection 9) zone positioning 10) perception 11) combat / death 12) taunts / audio.
  * **States:** `SearchingForPlayer` → `StealthyPursuit` → `GetOutOfSight` → `AggressivePursuit` → `Idle` → `PushTarget`. Animation is driven by `AnimState` over `DoAnimationClientRpc`, with cached `Animator.StringToHash` trigger ids.
  * **Multiple gargoyles coordinate through static state** — `gargoyleTargets` and `playerPushStates` are `ConcurrentDictionary`, plus an `activeGargoyles` list and a `PlayerPushStatesLock`. **Anything you add that must not double up across instances belongs in that static layer, and anything you read from it must tolerate another instance mutating it mid-tick.**
  * `bufferDistances` maps the eight `RelativeZone` values to how close the gargoyle will sit — that table is the "creepy but not overbearing" tuning surface, and it is deliberately asymmetric (3m behind you, 15m in front).
* **Audio — `Plugin\src\Utility\AudioManager.cs`, and it is the most surprising subsystem in the mod.**
  * Clips are **files on disk, not bundle assets**: defaults ship in the package's `Voice Lines\` folder, user additions go in `<game root>\Lethal Gargoyles\Custom Voice Lines\`. `GetMP3Files(category, folder)` maps a category name to its subfolder (`"General"` → `Taunt - General`, `"Attack"` → `Combat Dialog\Attack`, …) — despite the name it reads whatever it finds, and **only OGG actually survives the pipeline**.
  * **The host loads every enabled clip and pushes the raw bytes to each client over `CustomMessagingManager`**, named message `"SendLGAudioClip"`, `ReliableFragmentedSequenced`, one clip at a time behind a ready-handshake (`SetClientReadyServerRpc` / `SetClientReadyClientRpc`, 5s timeout, then it sends anyway). **Hard cap 512000 bytes (500KB) per clip — over it, the send is skipped with a `LogError` and the loop `break`s, so ONE oversized file silently costs the rest of its category.** Clients decode with `NVorbis.VorbisReader`.
  * **Clips are addressed BY NAME across the wire.** `TauntClientRpc(clipName, clipType)` sends a string; the client resolves it against its own list for that type and, if it isn't there, **does nothing at all** — no log outside a DEBUG build. A client that missed a transfer is therefore a *silent* failure that looks like "the gargoyle just isn't talking."
  * `OnNetworkDespawn` clears all eleven static lists. They are static, so they survive a lobby — clearing is what stops clip lists from doubling on the next round.
  * **Adding a voice-line CATEGORY is a SEVEN-place change; miss one and it fails quietly. Load the `voice-line` skill — it carries the table.** The seventh is the one that gets missed: **`Scrap\GargoyleStatue.cs` has its OWN parallel copy of the `clipType` switch**, so skipping it leaves the monster taunting correctly while the scrap silently plays nothing. (**Corrected 2026-08-15 (b4) — this file said "six" and omitted the scrap entirely; an `Explore` sweep found it, along with a third, optional switch in `LethalGargoylesAI.OtherTaunt`.**) Adding a *file* to an existing category needs none of it — picked up at load, and the config toggle is minted generically.
  * **SteamID taunts** are files named `<SteamID>[optional text].ogg` in `Taunt - SteamIDs`, played at a deliberate **2.5% chance** so they don't wear out.
* **Config — `Plugin\src\Config\Configuration.cs`.** Hand-written `cfg.Bind` entries plus `InitializeAudioClipConfigs`, which mints one `Enable <clipname>` toggle per discovered clip under `Audio.<Category>`. `ClearUnusedEntries` then reaches into BepInEx's private `OrphanedEntries` by reflection to prune stale toggles. **That reflection is load-bearing and undocumented in BepInEx — if a BepInEx 5 update renames that property, config pruning breaks silently.**
* **Patches — `Plugin\src\Patch\`.** `NetworkObjectManager` postfixes `GameNetworkManager.Start` to load the `LGNetworkHandler` prefab, attach `AudioManager` to it and register it, then postfixes `StartOfRound.Awake` to instantiate + `Spawn()` it **host-side only**. `StartOfRoundPatch` (`GetDeathCauses`) postfixes `WritePlayerNotes` to snapshot last round's deaths — vanilla cause always, plus Coroner's when loaded — which is what feeds the PriorDeath taunts. `AIHelperPatches` tracks player activity (kills, item grabs, facility time) for the Activity taunts; the watched items are the static `trackedItems` set on the AI (`Key`, `Apparatus`, `Comedy`, `Tragedy`, `Maneater`).
* **Scrap — `Plugin\src\Scrap\GargoyleStatue.cs`.** Registered only when `enableScrap`; the Eyeless Dog can hear it when `dogHear` is on, with `dogCooldown` between dog taunts.

## Build & Deploy

* **Debug build (`dotnet build`, or F5 in VS) does all of this automatically:** compile → `NetcodePatch` → `CopyToTestProfile` (from `LethalGargoyles.csproj.user`), which copies the patched DLL, `gargoyleassets`, `manifest.json`, the Coroner strings XML, NVorbis, and the whole `Voice Lines` tree into `<PluginsDirectory>\DropDaDeuce.LethalGargoyles-DEV\`. **So a plain debug build IS the deploy to the Gale `Dev` profile — there is no separate copy step, and you should not invent one.**
* **Release build additionally runs `PackThunderstore`** — `dotnet tcli build` against `Plugin\Thunderstore\thunderstore.toml`, output to `Plugin\Thunderstore\Packages\`. It packages from `bin\Release\`, and the version stamped on the package comes from the csproj `<Version>`.
* **Shipping a release means three numbers agreeing:** csproj `<Version>`, `manifest.json` `version_number`, and the top heading of `CHANGELOG.md`. Nothing enforces that — check it by hand.
* **You can build; you cannot test.** Running the game, joining a lobby, and hearing the gargoyle are Mathew's steps. Say plainly when a change is unverifiable without an in-game run, and give him the specific thing to watch or listen for.

## Do-not-relearn

* **A build that suddenly fails on a game type is a GAME UPDATE, not a regression in your change** — the game is a moving target and `Assembly-CSharp.dll` changes under the mod without warning. **Do not guess at the replacement API. Reflect over the installed assembly and read it.** The technique that settled `exitPoint` in minutes, and works for any game type:
  ```
  # a .NET 10 single-file script, run with: dotnet run reflect.cs
  #:package System.Reflection.MetadataLoadContext@9.0.0
  # PathAssemblyResolver over <game>\Lethal Company_Data\Managed\*.dll, then
  # LoadFromAssemblyPath("Assembly-CSharp.dll").GetType("EntranceTeleport")
  # and enumerate GetFields(Public|NonPublic|Instance) - it needs no game running,
  # loads nothing, and shows private members so publicizer behaviour never confuses the answer.
  ```
  Grepping the DLL for the member name is NOT sufficient — `exitPoint` appears in the binary's string heap while the field itself is gone, because `exitPointDoesntExist` shares the prefix.
* A **silent gargoyle on one client only** is almost always the audio transfer, not the AI: check that client's log for `Sent Clip(...)` / `Clip Loaded:` lines and for the 500KB `LogError`.
* An **RPC that appears to do nothing** is almost always a missing netcode-patch pass on a hand-moved DLL.
* **`GrabbableObject.ItemActivate` is REPLICATED BY VANILLA to every machine — it does NOT run only on the activating client.** Proven 2026-08-16 by an instrumented log showing the host running it for a client-held item (`server=True owner=False heldBy=Player #1`). So `GargoyleStatue.ItemActivate`'s `if (IsServer && ...)` guard on the `ItemActivateServerRpc` send is **load-bearing: it is what makes exactly one machine forward the request.** Removing it multiplies the taunt by machine count — two players, two voices. b8 removed it on an audit finding that claimed the statue was mute for non-hosts; **that finding was false**, the host's replicated copy had always fired the taunt. **The general rule this corrects: "guard every RPC send with `IsServer`" is not only about ClientRpcs — a ServerRpc sent from a vanilla-replicated callback needs the same guard, for a different reason.**
* **When a repro has two candidate multipliers sitting at the same number, vary one before theorising.** The statue bug first appeared as "2 statues held → 2 taunts" with 2 players connected. Item count and machine count were both 2; this cost two wrong fixes aimed at item count. One single-player run with 2 statues (→ 1 taunt) separated them instantly. Prefer changing the test over adding a hypothesis.
* A **`TypeLoadException` with no obvious line** is almost always a soft-dep type referenced outside its `Is*Loaded` guard.
* A **prefab/animation change that "didn't take"** is almost always a stale `gargoyleassets` — the plugin DLL rebuilt, the bundle did not.
* **`CopyToTestProfile` is guarded `Condition="'$(Configuration)' == 'Debug'"` and that condition is LOAD-BEARING — do not remove it.** Until 2026-08-16 (b19) it had no condition, so **a Release build silently overwrote the Debug DLL in the Gale `Dev` profile** and nothing in the build output said so. Mathew then playtests a Release DLL where every `[Conditional("DEBUG")]` line is absent, which reads exactly like "the logging you told me to look for isn't there." It bit twice in one day, the second time between two concurrent sessions. **The check takes one command: the `-DEV` folder's DLL should be the LARGER of the two in `Plugin\bin\` (Debug ~169 KB vs Release ~148 KB).** Do it before writing any playtest instruction that mentions a log line. The NVorbis copies in that target hardcode `bin/debug/` and are only correct because of the condition.
* `Plugin\src\Enemy\GargoyleUnityScripts.cs` is 18 lines — the Unity-side script stubs. Don't go looking for AI behaviour in it.
